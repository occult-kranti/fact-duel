# FACT//DUEL product UX review — loop 1

Date: 12 September 2026. Advisor scope: inspected `app/arena.tsx`, `app/globals.css`, and `README.md` in `/workspace/sites/fact-duel-online`. Applied the installed `trivia-duel-review` skill. This is source inspection, not a rendered-device usability study or official certification. No Site code was changed by this advisor.

## Executive product decision

Lead with a compact knowledge club: **pick an interest, play one round, discover a sourced fact, choose another challenge**. Use Quick Draw as the first encounter, an explicitly random practice bot as the default rival, and friend play as a clear parallel path. Collections should describe available facts honestly. Device-local history should reward learning from genuine play, with no invented global rank, population, streak or mastery. Keep the existing server acceptance/settlement protocol while redesigning the presentation.

The existing surface emphasizes configuring a timing experiment before experiencing a game. The proposed surface should reverse that hierarchy: play and learning first; detailed timing, market research and product progress in secondary places. Do not remove the concise rules people need to consent to play.

## Visual and behavioral direction

- **Palette:** warm paper/ink as a readable editorial default, deep midnight as the alternate theme, one strong electric blue or violet for primary action, a separate warm coral/accent for sports and cool mint/cyan for science. Use accents to identify domains, never as the only cue for correctness. Avoid assigning “green” to both selected and verified-correct before reveal. Contrast must be measured on final tokens, including muted text, borders, disabled controls and light-theme badges.
- **Typography:** a distinct display face may establish the brand at large sizes; questions and answers need a familiar highly readable UI face. Use stable tabular numerals for timers. Keep all-uppercase microcopy scarce, especially on mobile. Long scientific words and club names need wrapping behavior.
- **Art:** one light, purposeful hero treatment is sufficient. Give collection cards simple domain motifs; do not spend viewport height on large decoration before play. Avoid fake live avatars or activity feeds. Real users and simulated bots must remain distinguishable.
- **Hooks:** curiosity (“what fact will you learn?”), competence from source-backed correction, agency in choosing a collection, and consensual friend challenge. A local journal is a useful return path. Avoid expiring streak pressure, loss-chasing prompts, paid coin framing and artificial scarcity.
- **Motion:** short mode-selection transitions and restrained result reveals; no pulsing answer target or moving button during a timed question. Respect reduced motion. Motion never delays the moment the question is readable while the measurement clock runs.

## Robust flow state contract

| State | Required visible behavior | Guard / recovery |
|---|---|---|
| Catalogue loading | Skeleton or brief “Loading collections”; play unavailable for a known reason | Retry action on failure; no fake empty collection count |
| Lobby ready | Supported mode and actual pool shown; one primary action | Keep config mutable until request draft is committed |
| Creating/joining | Button becomes busy; duplicate submits disabled | Retry uses prior draft identity; changing config clears only an uncommitted draft |
| Waiting for friend | Invite, seat status, add-bot option for host | If friend and bot contend for a seat, server outcome wins; explain conflict |
| Preparing countdown | Plain readiness/connection status | No question clock before reveal; failed connection allows explicit retry |
| Question visible | Four choices, timer, one-attempt rule | Same semantic inputs for pointer and keyboard; no editing after lock |
| Local lock / sending | Selected answer remains visible | Immutable retry; no correctness leak |
| Server accepted | “Answer received”; no additional submit | Wait for other attempt/deadline without suggesting the UI is stuck |
| Between rounds | Correct fact and current score; ready for next | Bot automatically ready; no second match entry charged |
| Complete | Win/draw/loss, explanation and next action | Journal deduplicates terminal observation; settlement remains server-owned |
| Cancelled / expired | Explain cause and refund scope | Explicit fresh match; do not count as a win, learning streak or completed competitive round |
| Background/reload | Preserve existing active-match cancellation rule visibly | Document known mobile behavior; do not imply seamless background reconnect |
